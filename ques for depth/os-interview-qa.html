OS Fundamentals
Q1 – Q10

An OS is system software that manages hardware and provides an environment for application programs to run. It acts as an intermediary between users and hardware.

  • Process management – creation, scheduling, termination, synchronization
  • Memory management – allocation, paging, virtual memory
  • File system management – files, directories, permissions
  • Device management – drivers, I/O scheduling, buffering
  • Security & protection – user authentication, access control
💡 Think: OS = resource manager + extended machine + control program.

The kernel is the core of the OS running in privileged mode. It handles syscalls, scheduling, memory, and drivers.

FeatureMonolithic (Linux, Unix)Microkernel (Minix, QNX)
StructureAll services in kernel spaceMinimal kernel; services in user space
PerformanceFast (direct calls)Slower (IPC overhead)
ReliabilityBug can crash whole OSService crash is isolated
SizeLargeSmall
🔍 Linux is monolithic but modular — drivers loadable as kernel modules.

CPU runs in two privilege levels (mode bit): kernel mode (0) can execute any instruction; user mode (1) is restricted. A system call is a controlled trap into the kernel requesting a privileged service.

// user program → libc wrapper → trap → kernel handler
write(1, "hi", 2);  // → SYS_write → mode switch → kernel → return
⚠️ Mode switch ≠ context switch. Mode switch keeps same process; context switch changes process (heavier).
  • Batch – jobs grouped, no interaction (payroll 1970s)
  • Time-sharing / Multitasking – CPU multiplexed, interactive (Unix, Windows)
  • Real-time (RTOS) – deterministic deadlines; hard vs soft (VxWorks, FreeRTOS)
  • Distributed – multiple machines appear as one (Amiga, cloud OS)
  • Embedded / Mobile – resource constrained (Android, iOS)
  • Multiprocessor – SMP vs NUMA scheduling concerns

Booting loads the OS into memory from power-on:

  1. BIOS/UEFI POST → finds boot device
  2. Bootloader (GRUB) stage 1/2 loads kernel image
  3. Kernel initializes drivers, mounts root fs
  4. init / systemd (PID 1) starts user-space services
💡 Bootstrap paradox: tiny firmware pulls itself up by loading bigger loader, which loads the OS.

All transfer control via the interrupt vector table to an ISR, saving state first.

  • Addressable RAM: 32-bit ≈ 4 GB; 64-bit ≈ 16 EB (practically TBs)
  • Registers & data paths wider — faster for 64-bit math
  • Pointer size doubles (4 → 8 bytes) — slightly more memory use
  • 64-bit OS can run 32-bit apps (WOW64 / multilib); reverse is impossible

Shell is a user-space command interpreter (bash, zsh, PowerShell) that parses commands and invokes syscalls. Kernel does the real work — shell just asks.

$ ls -l  # shell parses → fork+exec /bin/ls → ls uses getdents() syscall

Processes
Q11 – Q20

Program = passive code on disk. Process = active execution with PC, stack, heap, registers, and OS resources. One program can spawn many processes.

💡 Analogy: program is a recipe; process is the cooking in progress.

PCB (Process Control Block) is the OS's per-process record: PID, state, PC, registers, scheduling priority, memory maps, open files, I/O status, accounting.

Context switch saves/restores PCB state so another process can run. It is pure overhead — no user work done — costing ~1–10 µs (register/Dispatch + cache/TLB pollution).

// steps: save PC+regs → PCB → ready queue → scheduler picks next → load its PCB → flush TLB → resume
NEW → READY → RUNNING → TERMINATED
          ↑       ↓↕
       WAITING (I/O wait)
       + SUSPENDED variants when swapped out
  • New: being created
  • Ready: runnable, waiting for CPU
  • Running: executing on CPU
  • Waiting/Blocked: waiting for event/I/O
  • Terminated: finished, awaiting cleanup
🔍 Only one Running per core; many Ready/Waiting. Scheduler moves Ready→Running; I/O moves Running→Waiting→Ready.
pid_t pid = fork();  // returns 0 to child, pid to parent, -1 on fail
if (pid == 0) {
  execlp("ls", "ls", NULL);  // child replaces image
} else {
  wait(NULL);  // parent waits for child
}
  • fork: clones address space (copy-on-write), duplicates FDs
  • exec: replaces image, keeps PID/FDs
  • wait: blocks for child, reaps exit status
  • exit: terminates, sends SIGCHLD
TypeWhatFix
ZombieTerminated but parent hasn't wait()ed; PCB lingersParent must wait(); init reaps if parent dies
OrphanParent died first; adopted by init/systemdHarmless — init reaps
DaemonBackground service, no terminal (sshd, systemd)Intentional
⚠️ Too many zombies = parent bug leaking PIDs. Check with ps aux | grep 'Z'.

Instead of copying all pages on fork(), parent and child share read-only pages. On first write, a fault copies just that page. Makes fork+exec cheap.

💡 Why fork is fast in Linux despite huge processes — only page tables copied initially.

Limits via max PIDs, ulimit -u (RLIMIT_NPROC), cgroups, memory overcommit policy. A fork bomb (:(){ :|:& };:) exponentially forks until PID/memory exhaustion.

⚠️ Defenses: per-user process limits, cgroup pids.max, and overcommit + OOM killer.

Q21 – Q28

MemorySeparate address spaceShared within process
OverheadHeavy (PCB, page tables)Light (TCB: stack + regs)

  • Shared: code, data/heap, open files, signal handlers, PID
  • Private (per-thread): stack, program counter, registers, thread ID, errno, TLS
⚠️ Shared stack mistake = classic bug: never return pointer to thread's stack local.
  • User threads: managed by library, kernel sees 1 process — fast switch, but blocking syscall blocks all
  • Kernel threads: OS-scheduled, true parallelism — costlier switch

Models: Many-to-One, One-to-One (Linux NPTL, Windows), Many-to-Many (scheduler activations).

Pre-created pool of worker threads fed by a task queue. Avoids per-request thread create/destroy cost and bounds concurrency to avoid thrashing.

// concept: workers block on queue; submitter enqueues
pool.submit(task);  // worker picks up, runs, returns to pool

Benefits: responsiveness (UI stays alive), resource sharing, economy (cheaper than fork), parallelism on multicore.

Challenges: races, deadlocks, non-determinism, Amdahl's law limits — serial part dominates.

🔍 Amdahl: speedup = 1 / ((1-p) + p/n). 90% parallel on 8 cores → max ~4.7×.

Because threads share memory, unsynchronized count++ (read-modify-write) can interleave and lose updates. Sync enforces mutual exclusion + ordering via mutexes, semaphores, condition variables, barriers.

Per-thread global-like variable — same name, different instance per thread. Used for errno, RNG state, per-thread caches without locking.

__thread int my_id;  // C/GCC TLS — each thread has its own copy

Linux implements threads as tasks sharing resources via clone(CLONE_VM|CLONE_FS|CLONE_FILES|...). NPTL (1:1 model) maps each pthread to a kernel task. Check with ps -eLf.

CPU Scheduling
Q29 – Q40
  • Preemptive: OS can forcibly take CPU (timer interrupt) — responsive, needs careful sync
  • Non-preemptive: process runs till it yields/blocks — simple, but one hog blocks all
💡 Modern desktop/server OS are preemptive. Early Mac/Windows 3.x were cooperative.
  • Turnaround (TAT) = Completion − Arrival
  • Waiting = TAT − Burst (time spent in ready queue)
  • Response = FirstRun − Arrival (interactivity)
  • Throughput = jobs/sec; Utilization = % CPU busy; Fairness
🔍 Optimize avg TAT for batch, response for interactive, deadlines for real-time, fairness overall.

FCFS runs in arrival order, non-preemptive. Simple and fair but avg wait can be huge. Convoy effect: one long job blocks all short jobs behind it (like a truck convoy).

P1=24ms, P2=3ms, P3=3ms arrive together
FCFS avg wait = (0+24+27)/3 = 17ms  // vs SJF = (0+3+6)/3 = 3ms

SJF (non-preemptive) / SRTF (preemptive) pick smallest next/remaining burst → provably minimal avg waiting time. Impractical because future burst unknown — OS predicts via exponential averaging of history. SRTF also risks starvation of long jobs.

Each process gets fixed quantum q cyclically, preempted on expiry. Too large → FCFS; too small → thrashing on context switches. Rule of thumb: q should be large vs switch cost (e.g., 10–100 ms) but small vs interactive need.

⚠️ If q=10ms and switch=1ms, 10% overhead. If q=1ms, 50%+ overhead.

Highest priority runs first (preemptive or not). Problem: low-priority jobs starve if high-priority stream never ends. Aging gradually raises waiting jobs' priority so they eventually run.

  • MLQ: separate queues (system > interactive > batch), fixed priority, no movement between queues
  • MLFQ: jobs migrate — new jobs start high; if they use full quantum they drop down. Approximates SJF without knowing bursts + prevents starvation via periodic boost
💡 MLFQ is the basis of real schedulers (BSD, Windows, Linux CFS conceptually).

Linux uses CFS (Completely Fair Scheduler) for normal tasks + RT classes (FIFO/RR, deadline) for real-time. CFS tracks vruntime (weighted run time); always picks smallest vruntime → fairness proportional to nice weights. O(log n) red-black tree.

$ nice -n 10 ./low &  # lower weight → less CPU
$ chrt -f 50 ./rt-task  # SCHED_FIFO realtime

Dispatch latency = time to stop one process and start another (save/restore + scheduler + TLB/cache effects). Pure overhead — that is why quantum ≫ switch time.

CPU-bound hogs CPU, rarely blocks. I/O-bound blocks often, needs quick wakeup. Good schedulers favor I/O-bound (short bursts first, priority boost on wakeup) to keep devices busy while CPU-bound fills gaps.

Synchronization
Q41 – Q52

Race: output depends on uncontrolled timing of concurrent accesses. Critical section: code touching shared state that must run atomically. Solution must guarantee mutual exclusion + progress + bounded waiting.

// both threads run counter++ → lost update possible
int tmp = counter; tmp++; counter = tmp; // interleave = lost write

Peterson's is a software-only 2-process mutual exclusion using flag[] + turn. Correct but busy-waits and doesn't scale. TestAndSet / CompareAndSwap are hardware atomics forming spinlocks:

while (TestAndSet(&lock)); // spin
// critical section
lock = false;
MutexSemaphoreSpinlock
ValueBinary + ownershipCounting, no ownerBusy-wait flag
Blocks?Yes (sleep)Yes (sleep)No (burns CPU)
UseExclusive accessResource pool / signalingShort waits, multicore kernel
⚠️ Mutex is not just binary semaphore — only the locker can unlock a mutex; any thread can signal a semaphore.
sem_init(&mutex, 0, 1);  // binary — mutual exclusion
sem_init(&slots, 0, 5);  // counting — 5 identical resources
sem_wait(&slots); // P(): dec, block if <0
// ... use resource ...
sem_post(&slots); // V(): inc, wake waiter

Monitor = mutex + condition variables bundled with shared data. Only one thread inside at a time; others wait() on conditions and are signal()ed. Java synchronized + wait/notify is a monitor.

sem empty=N, full=0, mutex=1;
Producer: wait(empty); wait(mutex); put(item); signal(mutex); signal(full);
Consumer: wait(full);  wait(mutex); take(item); signal(mutex); signal(empty);
⚠️ Order matters: wait(mutex) before wait(empty) can deadlock. Always wait on counting sems first.

Multiple readers OK together; writers need exclusivity. First-readers-preference can starve writers; writers-preference / fair (queue) fixes. pthread_rwlock_t implements it.

5 philosophers, 5 forks — need 2 forks to eat. Naïve take-left-then-right deadlocks if all grab left. Fixes: limit to 4 eaters, odd/even ordering, try-and-backoff, central arbitrator (monitor).

Inversion: low-prio holds lock needed by high-prio, but medium-prio preempts low → high waits unboundedly (crashed Mars Pathfinder!). Inheritance: lock-holder temporarily inherits highest waiter priority. Also priority ceiling protocol.

Blocking sleeps via scheduler (good for long waits). Spinning burns CPU (good only for very short waits on multicore where wakeup cost > spin cost). Modern mutexes spin briefly then block (adaptive).

Atomics complete indivisibly (no interleave). CAS(addr, expected, new) swaps only if current==expected — basis of lock-free structures.

do { old = *p; } while (!CAS(p, old, old+1)); // lock-free increment
  • Barrier: N threads rendezvous; all released together (phased computation)
  • Lock-free: some thread always progresses (CAS retry)
  • Wait-free: every thread progresses in bounded steps (strongest, hardest)

Deadlocks
Q53 – Q60

Set of processes each waiting for a resource held by another — none can proceed.

T1: lock(A); lock(B);  // T2 does lock(B); lock(A) → deadlock possible
T2: lock(B); lock(A);
  1. Mutual exclusion – resource non-sharable
  2. Hold and wait – holding one while requesting another
  3. No preemption – can't forcibly take it away
  4. Circular wait – chain P1→P2→…→P1
💡 All four must hold. Break any one → no deadlock.
StrategyIdeaCost
PreventionBreak a Coffman condition (ordering, preemption, spooling)Restrictive, wasteful
Avoidance (Banker's)Check each grant keeps a safe sequenceNeeds max claims upfront
DetectionAllow, periodically check RAG cycle; kill/rollbackOccasional freeze + kill
Ignore (Ostrich)What Linux/Windows do mostly!Reboot if unlucky

Banker grants a request only if a safe sequence still exists (all processes can finish with Available + future releases). Uses Max, Allocation, Need=Max−Alloc matrices. O(n²·m). Conservative — may deny safe-enough grants.

Nodes = processes (circles) + resources (squares, dots=instances). Edges: request → , allocation ← . Single-instance: cycle = deadlock. Multi-instance: cycle = possible deadlock (need Banker's-style check).

Threads doingFix
DeadlockBlocked foreverOrdering, timeouts
LivelockRunning but retrying forever (polite collision)Randomized backoff
StarvationNever scheduledAging, fairness
  • Global lock ordering — always acquire A before B
  • Try-lock with timeout + backoff
  • Hold-and-wait denial — grab all or none
  • Minimize critical section, avoid calling unknown code while holding locks
  • Use lock hierarchies / static analysis / thread sanitizer

Most general OSes use the Ostrich algorithm — ignore the problem — because deadlocks are rare and prevention is expensive. Recovery when detected: kill processes (victim selection), preempt resources + rollback, or reboot. DBs do real detection (wait-for graph + timeouts).

Memory Management
Q61 – Q70

Logical (virtual): what CPU generates. Physical: real RAM location. MMU translates at runtime via page tables + TLB: physical = frame × size + offset. Enables isolation + relocation.

  • Fixed (MFT): memory split into fixed partitions — simple, suffers internal fragmentation
  • Dynamic (MVT): partitions sized to jobs — suffers external fragmentation (holes)

Placement: first-fit (fast), best-fit (smallest hole, many slivers), worst-fit (largest hole).

  • Internal: wasted space inside allocated block (fixed sizes)
  • External: wasted space between blocks (holes too small scattered)

Compaction shuffles processes together to merge holes — expensive (needs relocation) and impossible if pinned I/O. Paging eliminates external fragmentation.

Paging divides virtual memory into fixed pages and RAM into frames. Page table maps page→frame. No external fragmentation; small internal waste (last page).

VA = [page# | offset]  →  PT[page#] = frame  →  PA = [frame | offset]
// e.g. 32-bit, 4KB pages: 20-bit page#, 12-bit offset
💡 Per-process page tables give isolation. Shared pages enable shared libs/CoW.
PagingSegmentation
UnitFixed pages (4KB)Variable logical segments (code/data/stack)
FragmentationInternal onlyExternal
ViewProgrammer invisibleProgrammer visible, protection per segment

x86 historically used segmented paging — segments for protection, pages for allocation.

TLB is a tiny MMU cache of recent page translations. Hit (~1 cycle) avoids 1–4 memory accesses for page-table walk. TLB shootdown/flush on context switch is a major switch cost; ASIDs/tags reduce flushes.

🔍 Effective access = hit×(TLB+mem) + miss×(TLB+walk+mem). 99% hit → ~2× mem time.
  • Multilevel: page the page table (e.g., 2-level for 32-bit, 4-level for 48-bit VA) — only allocate needed subtrees
  • Inverted: one entry per physical frame (PID+page) — small, but lookup needs hash
  • Valid-invalid bit: marks legal pages; invalid → segfault. Also dirty, referenced, protection bits
  • Static: library copied into binary — big, but portable, fast start
  • Dynamic (.so/.dll): linked at load/run — small binaries, shared RAM pages, but DLL hell + startup cost

Swapping moves whole processes (or pages) to disk to free RAM. Still relevant: swap for hibernation, rarely-touched pages, memory overcommit safety, and OOM grace. Thrashing if overused on HDD.

StackHeap
Managed byCompiler (LIFO)Programmer/GC (malloc/free)
SpeedVery fastSlower + fragmented
BugsOverflow (deep recursion)Leak, double-free, use-after-free

Virtual Memory
Q71 – Q80

Illusion of huge private memory backed partly by disk. Gives: run programs bigger than RAM, isolation, efficient sharing, easy relocation, sparse address spaces (heap grows up, stack down).

Load pages only on first touch. Fault flow:

  1. MMU faults (invalid bit), traps to kernel
  2. Validate address — kill if illegal (segfault)
  3. Find free frame (evict if needed)
  4. Read page from disk, update PT, restart instruction
💡 Pure demand paging starts with zero pages loaded — many initial faults (locality helps after).
AlgoVictimNotes
FIFOOldest loadedSimple, suffers Belady's
OptimalFarthest future useTheoretical lower bound
LRULeast recently usedGreat, needs timestamps/counters
Clock (2nd chance)Sweep with ref bitPractical LRU approx (Linux)

More frames → more faults for some patterns under FIFO (e.g., 1-2-3-4-1-2-5-1-2-3-4-5). Stack algorithms (LRU, Optimal) never suffer it — FIFO does because it ignores recency.

⚠️ Favorite interview trap: "Does more memory always help?" — Not with FIFO!

Thrashing = CPU wasted on paging instead of work (high fault rate, low CPU util, disk 100%). Causes: over-multiprogramming beyond working sets.

Fix: reduce multiprogramming (suspend/swap out), add RAM, use working-set / page-fault-frequency control, kill hogs.

Working set W(t,Δ) = pages touched in last Δ. Keep each process's WS resident → no thrashing. PFF adjusts frames: faults too high → grow allocation; too low → shrink.

  • CoW: fork shares read-only; copy on write (fast fork)
  • mmap: map file into VA — lazy paging handles I/O; great for big files, IPC, shared libs
  • Shared mem: explicit SHM segment mapped in multiple processes
EAT = (1-p) × mem + p × fault_time
// p=1/1000, mem=100ns, fault=8ms → EAT ≈ 8.1µs (80× slower!)
💡 Even tiny fault rates dominate — locality is everything.

4KB balances internal waste vs table size vs I/O granularity. Huge pages (2MB/1GB) cut TLB misses for DBs/HPC (fewer entries cover more), but waste memory and need special alloc (hugetlbfs).

When RAM+swap exhausted, Linux OOM killer sacrifices a badness-scored process (big, non-root, non-critical) to save the kernel. Tune via /proc/<pid>/oom_score_adj. Containers hit cgroup OOM first.

File Systems
Q81 – Q88

Attributes: name, type, size, permissions, timestamps, owner, blocks. Ops: create/open/read/write/seek/truncate/close/delete.

Access: sequential (tape), direct/random (disk offset), indexed (index block → records, DBs).

Inode = metadata + block pointers (no filename; dirs map names→inodes). Hard link: another name for same inode (same fs, refcount; survives original delete). Soft/symlink: path pointer (cross-fs, breaks if target moves).

$ ln file hard && ln -s file soft && ls -i  # same inode for hard

Disk & I/O
Q89 – Q96

Data on platters → tracks → sectors. Access = seek (move arm, ~ms) + rotational latency (½ spin) + transfer. Seek dominates — scheduling minimizes it. SSDs have no seek (µs).

  • Polling: CPU busy-loops checking device — simple, wasteful
  • Interrupts: device signals done — CPU free meanwhile
  • DMA: controller moves bulk data RAM↔device without CPU; CPU only interrupted at end
  • Blocking: call sleeps till done
  • Non-blocking: returns EAGAIN immediately; app polls
  • Async (aio, io_uring): submit + completion callback/queue

Multiplexing: select/poll O(n) scan; epoll/kqueue O(1) event-driven — basis of Nginx/Node scale.

Kernel stages data so CPU and device overlap. Double buffering: fill one buffer while app consumes the other — hides device latency for streaming.

  • Wear leveling: FTL spreads writes evenly
  • Write amplification: 1 app write → multiple NAND writes (GC + erase-block mismatch); lower is better
  • TRIM: OS hints dead pages so GC skips them

Low-level (factory): sectors + ECC. Partition + logical: create FS structures (inodes, FAT). Bad blocks remapped via spare sectors (SMART) or marked in FAT.

Linux & Unix

  2. GRUB loads vmlinuz + initramfs
  3. Kernel inits, mounts root, runs PID 1 (systemd)
