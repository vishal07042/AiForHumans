DBMS Fundamentals
Q1 – Q10

DBMS is software to store, manage, and query data with abstraction, security, concurrency, and recovery.

File SystemDBMS
RedundancyHigh, uncontrolled duplicationControlled via normalization
IntegrityApp-enforcedConstraints enforced centrally
ConcurrencyNone / manualACID transactions, locking
RecoveryNoneLogging, crash recovery
QueryCustom codeDeclarative SQL + optimizer
  • Physical: how data stored (files, indexes)
  • Logical: what data stored (tables, relations)
  • View: what users see (projections, authorization)

Data independence: physical changes don't break apps (physical independence); logical changes minimally affect views (logical independence).

RDBMSNoSQL
ModelTables, fixed schema, joinsDoc / key-value / column / graph, flexible
ScaleVertical + read replicasHorizontal sharding native
ConsistencyStrong ACIDOften BASE / tunable
ExamplesPostgres, MySQLMongoDB, Redis, Cassandra
💡 Rule: need joins + strong consistency → RDBMS; massive scale / flexible shape → NoSQL.
  • Hierarchical: tree (IMS) — fast, rigid
  • Network: graph with pointers (CODASYL) — flexible, complex
  • Relational: tables + declarative keys — dominant
  • OO / OR: objects + methods; Postgres is object-relational
-- DDL: structure (auto-commit)
CREATE TABLE t(id INT PRIMARY KEY); ALTER TABLE t ADD c TEXT;
-- DML: data
SELECT * FROM t; INSERT INTO t VALUES(1); UPDATE t SET c='x';
-- DCL: permissions
GRANT SELECT ON t TO app; REVOKE ALL ON t FROM app;
-- TCL: transactions
COMMIT; ROLLBACK; SAVEPOINT s1;

Schema = design/blueprint (tables, types). Instance/state = data at a moment. Schema changes rarely; instance changes constantly. Empty DB still has a schema.

  • 1-tier: embedded (SQLite in app)
  • 2-tier: client ↔ DB server directly
  • 3-tier: client ↔ app server ↔ DB — pooling, auth, logic in middle; web standard

Physical: change storage/indexes without rewriting apps. Logical: add columns/tables without breaking existing views (harder, needs views/compat). Achieved via layered schemas.

OLTPOLAP
WorkloadMany small writes (orders, payments)Few huge analytical reads
SchemaNormalizedStar/snowflake, denormalized
ExamplesPostgres, MySQLSnowflake, BigQuery, Redshift
🔍 HTAP (TiDB, Cockroach) tries both — fresh analytics on live OLTP data.
  1. Parser: syntax check + relational algebra tree
  2. Optimizer: cost-based plan (join order, index pick) via stats
  3. Executor: runs plan via storage engine (buffer pool, indexes)
💡 EXPLAIN shows the chosen plan — always check it before tuning SQL.

ER Model
Q11 – Q19
  • Entity: real-world object (Student #42)
  • Entity set: collection (Students table)
  • Attributes: simple/composite (name→first+last), single/multi-valued (phones), derived (age from dob)
  • Keys: super → candidate (minimal) → primary (chosen); alternate = leftover candidates

Strong: has own PK (Student). Weak: no PK, depends on owner via identifying relationship (Room needs Building + room_no). Partial key (room_no) + owner PK = full key. Weak drawn double-rectangle.

  • Degree: unary, binary, ternary (entities involved)
  • Cardinality: 1:1, 1:N, M:N (how many can link)
  • Participation: total (must, double line — every employee works in a dept) vs partial (optional)
Student ──enrolls (M:N, total/partial)── Course
  • 1:1: FK on either side (or merge); put FK on total-participation side
  • 1:N: FK on N-side referencing 1-side PK
  • M:N: new junction table with both FKs (composite PK), plus relationship attributes
-- M:N Student-Course → Enrollment(student_id, course_id, grade)
PRIMARY KEY(student_id, course_id),
FOREIGN KEY(student_id) REFERENCES Student(id)

Total: every entity must participate (every loan must have a borrower → FK NOT NULL). Partial: may skip (a person may have zero loans). Total often → NOT NULL FK + cascade.

Specialization: top-down (Employee → Manager/Engineer). Generalization: bottom-up (Car+Bike → Vehicle). Map via: single table + type flag, per-subclass tables, or per-concrete tables. Disjoint vs overlapping, total vs partial constraints.

Treat a relationship as an entity to attach another relationship (e.g., Enrolls + Evaluated-by-TA → evaluation of an enrollment). Avoids ternary misuse; maps to extra FK table.

  1. Strong entities → tables with PK
  2. Weak entities → table with owner PK + partial key
  3. 1:1 / 1:N → FK placement
  4. M:N → junction table
  5. Multivalued attr → separate table
  6. Composite → flatten columns; derived → omit/compute
CREATE TABLE Employee(id INT PRIMARY KEY, mgr_id INT REFERENCES Employee(id));
-- CEO has NULL mgr_id; query hierarchy with recursive CTE

Relational Model
Q20 – Q28
  • Relation: table (set of tuples, no duplicates)
  • Tuple: row; Attribute: column; Domain: allowed values/type
  • Degree: #columns; Cardinality: #rows
  • NULL: unknown/missing — propagates in comparisons (3-valued logic)
KeyMeaning
SuperUniquely identifies (may have extra cols)
CandidateMinimal super (no subset works)
PrimaryChosen candidate (NOT NULL, stable)
AlternateCandidates not chosen (UNIQUE)
ForeignReferences another table's PK
CREATE TABLE Orders(
 id SERIAL PRIMARY KEY,        -- unique + not null + index, one per table
 email TEXT UNIQUE,                 -- unique, may allow one NULL (PG) / one NULL (MySQL)
 user_id INT REFERENCES Users(id) ON DELETE CASCADE);
⚠️ One table → one PK, many UNIQUEs. FK needs matching index or deletes will lock/scan.

FK must match a live PK or be NULL. Actions:

  • CASCADE: propagate delete/update
  • SET NULL / SET DEFAULT: orphan safely
  • RESTRICT / NO ACTION: block violating change
  • Entity: PK unique + NOT NULL
  • Referential: FK points to existing row
  • Domain: CHECK / type / NOT NULL (age >= 0)
  • Key: uniqueness enforcement
  • σ (select): filter rows — σ_age>20(Students)
  • π (project): pick columns — π_name(Students)
  • ⋈ (join): combine on condition; natural join on same names
  • ÷ (division): "for all" queries (students taking ALL courses)
  • Set ops: ∪ ∩ − require union-compatible schemas

Declarative "what", not "how". Tuple calculus: {t | Student(t) ∧ t.age > 20}. Domain calculus uses attribute variables. SQL is based on tuple calculus; algebra is procedural counterpart — equivalent power.

X → Y: X determines Y (same X ⇒ same Y). Armstrong: reflexivity (Y⊆X ⇒ X→Y), augmentation (X→Y ⇒ XZ→YZ), transitivity (X→Y,Y→Z ⇒ X→Z). Plus union/decomposition/pseudo-transitivity. Basis for normalization + closure computation.

-- R(A,B,C,D), F = {A→B, B→C, C→D}. Closure A+ = {A,B,C,D} → A is key.
-- Must-have: attrs never on RHS must be in every key. Useless: attrs never on LHS can't determine others.
💡 Interview trick: compute X+ by repeatedly adding RHS until fixpoint.

SQL Basics
Q29 – Q43
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
⚠️ That's why you can't use SELECT aliases in WHERE, but can in ORDER BY. HAVING filters groups; WHERE filters rows.
SELECT dept, COUNT(*) FROM Emp
WHERE salary > 50000      -- before grouping
GROUP BY dept
HAVING COUNT(*) > 5;       -- after grouping
INNER JOIN -- only matches
LEFT JOIN  -- all left + matched right (NULLs if none)
RIGHT JOIN -- mirror
FULL OUTER JOIN -- all from both
CROSS JOIN -- cartesian product
SELF JOIN  -- table to itself (manager hierarchy)
💡 INNER filters; OUTER preserves. COUNT(*) counts NULL-extended rows — use COUNT(col) to skip NULLs.
-- WRONG: turns LEFT JOIN into INNER (NULLs removed)
SELECT * FROM A LEFT JOIN B ON A.id=B.id WHERE B.x='p';
-- RIGHT: filter in ON to preserve left rows
SELECT * FROM A LEFT JOIN B ON A.id=B.id AND B.x='p';
  • UNION: distinct combined rows (sorts/dedups — slower)
  • UNION ALL: keeps duplicates (faster — default for logs)
  • INTERSECT / EXCEPT: common / difference (watch NULL semantics)
⚠️ Columns must match in count + compatible types. UNION ALL is almost always what you want for perf.
-- UNKNOWN, not TRUE/FALSE:
SELECT * FROM t WHERE col != 'x';  -- misses NULL rows!
SELECT * FROM t WHERE col NOT IN (SELECT c FROM u); -- empty if u.c has ANY NULL!
-- Fix: COALESCE, IS NULL, NOT EXISTS
WHERE COALESCE(col,'∅') != 'x';  WHERE NOT EXISTS(...);
DELETETRUNCATEDROP
WhatRows (filtered), loggedAll rows, deallocates pagesTable + schema gone
RollbackYesOften yes in txn (PG) / no (MySQL DDL)No (DDL)

Logically similar, physically: PK is the clustered index default (InnoDB/Postgres), one per table, used as FK target + row identity. UNIQUE creates secondary index. Prefer surrogate PK (bigint/uuid) + UNIQUE on natural keys.

CREATE TABLE Emp(
 id SERIAL PRIMARY KEY,
 age INT CHECK(age >= 18),
 status TEXT DEFAULT 'active' NOT NULL,
 dept_id INT REFERENCES Dept(id));
-- 2nd highest salary per dept:
SELECT dept, MAX(salary) FROM Emp
WHERE salary < (SELECT MAX(salary) FROM Emp e2 WHERE e2.dept=Emp.dept)
GROUP BY dept;
  • DISTINCT: dedup result rows; GROUP BY: per-group aggregates
  • COUNT(*): rows incl. NULLs; COUNT(col): non-NULL only; COUNT(DISTINCT col): unique non-NULL
  • Non-correlated: runs once (IN list) — optimizer often rewrites as join
  • Correlated: runs per outer row (EXISTS) — powerful, can be slow; EXISTS stops at first match
💡 Prefer EXISTS over IN when subquery has NULLs or is large.
WHERE id IN (SELECT id FROM B)          -- NULL trap if B has NULL
WHERE EXISTS (SELECT 1 FROM B WHERE B.id=A.id) -- NULL-safe, short-circuits
WHERE x > ALL(SELECT x FROM B)  -- greater than max
WHERE x > ANY(SELECT x FROM B)  -- greater than min
WHERE name LIKE 'An%'       -- prefix (index-usable with varchar_pattern_ops)
WHERE name ILIKE '%gupta%'    -- case-insensitive (PG)
WHERE email ~ '^[a-z]+@'      -- regex, use trigram index (pg_trgm)
-- Real search: tsvector/tsquery or Elastic, not LIKE '%...%'

OFFSET scans + discards — page 10000 is slow + unstable under writes. Keyset (seek) pagination is stable + fast:

-- instead of OFFSET 100000:
WHERE (created_at, id) < ($last_seen_ts, $last_seen_id)
ORDER BY created_at DESC, id DESC LIMIT 20;

Normalization
Q54 – Q64

Unnormalized tables duplicate facts → insert (can't add dept without employee), update (change dept name in 100 rows), delete (deleting last employee loses dept). Normalization splits facts so each lives once.

Each cell holds one indivisible value; no lists/arrays/CSV in a column. Split phones="a,b" into separate Phone table or array type (if DB supports + you query it properly).

⚠️ 1NF violation is the #1 real-world smell: comma-separated IDs kill joins + indexes.

Must be 1NF + every non-key attr depends on the WHOLE PK, not part. Enrollment(student_id, course_id → grade, student_name) violates (name needs only student_id) → split Student + Enrollment.

Must be 2NF + non-key attrs depend only on the key. Emp(id → dept_id, dept_name) has id→dept_id→dept_name (transitive) → split Dept(dept_id, dept_name).

BCNF: for every X→Y, X is a superkey. Stronger than 3NF. Classic: Course-Teacher-Room (teacher→room) can be 3NF but not BCNF → split. BCNF may lose dependency preservation (rare trade-off).

  • 4NF: no independent multi-valued facts in one table (employee→skills + employee→languages must split, else combinatorial explosion)
  • 5NF: no join dependency that isn't from keys (rare; decompose cyclic constraints)

Lossless: joining split tables gives back exactly original (no spurious rows) — test via chase / common superkey. Dependency-preserving: FDs checkable without joins. Ideal = both (always possible to 3NF; BCNF may sacrifice latter).

  • Read-heavy analytics (star schema, counts, pre-joined views)
  • Avoid expensive joins (store username in orders)
  • Use counters, materialized views, CQRS read models
💡 Normalize for writes, denormalize for reads — and guard with app/backfill + constraints.
ProsCons
Surrogate (id bigint/uuid)Stable, narrow, fast joinsNeeds extra UNIQUEs
Natural (email, isbn)MeaningfulChanges, wide, privacy
CompositeModels M:N truthWide FKs everywhere
Orders(order_id, customer_name, customer_city, product1, product2)
1NF: split products → OrderLines(order_id, product)
2NF: customer_name depends on customer only → Customers
3NF: city depends on customer → keep in Customers, not Orders
Result: Customers(id,name,city) Orders(id,cust_id) Lines(order_id,product)
  1. ER model → tables
  2. List FDs → normalize to 3NF/BCNF
  3. Pick PKs (surrogate) + FKs + UNIQUEs + CHECKs
  4. Index for access paths (not prematurely)
  5. Load-test + denormalize hot reads

Transactions
Q65 – Q74
  • Atomicity: all-or-nothing (undo on abort)
  • Consistency: DB moves valid→valid (constraints hold)
  • Isolation: concurrent txns don't see partial effects
  • Durability: committed survives crashes (WAL/flush)
BEGIN; UPDATE a SET bal=bal-100; UPDATE b SET bal=bal+100; COMMIT;
Active → Partially Committed → Committed
   ↓              ↓
  Failed → Aborted (rolled back)

Partially committed = executed but not yet durable; commit point = WAL flushed.

LevelAllowsPrevents
READ UNCOMMITTEDDirty readsNothing (rare)
READ COMMITTEDNon-repeatable, phantomDirty (PG/SQL default)
REPEATABLE READPhantom (some DBs)Dirty + non-repeatable
SERIALIZABLENothing (true serial order)All (+ predicate locks)
⚠️ Higher = safer but more aborts/locks. Default RC + row locking fits most apps.
  • Dirty: read uncommitted change that later rolls back
  • Non-repeatable: same row different values on re-read (UPDATE committed between)
  • Phantom: same query different ROW SET (INSERT committed between)

Schedule = interleaving of ops. Serial = no interleave. Serializable = result equals SOME serial order (via precedence graph acyclicity). Serializable ≠ serial — allows concurrency with same effect.

Edge Ti→Tj if they conflict (RW/WR/WW on same item, i before j). Acyclic → conflict-serializable. Cycle → abort/rollback one txn. This is what SSI (serializable snapshot isolation) checks.

BEGIN;
INSERT INTO t VALUES(1); SAVEPOINT s1;
INSERT INTO t VALUES(2); ROLLBACK TO s1;  -- keeps 1, drops 2
COMMIT;

Autocommit wraps each statement in its own txn — multi-statement transfers break atomicity. Fix: explicit BEGIN. MySQL implicitly commits on DDL; Postgres allows transactional DDL (safer migrations).

2PC: coordinator PREPAREs all (vote commit/abort) → if all yes, COMMIT else ABORT. Blocking if coordinator dies (need 3PC/Paxos-based). Modern: saga pattern (compensating txns) for microservices.

BASE (Basically Available, Soft state, Eventual): favor availability over instant consistency (feeds, carts, DNS). Use ACID for money/inventory; BASE for likes, recommendations, sessions.

Concurrency Control
Q75 – Q84

All stem from uncontrolled interleaving. Shared (S) locks allow reads; Exclusive (X) blocks all. 2PL + predicate locks progressively eliminate each anomaly up the isolation ladder.

  • 2PL: growing (acquire) then shrinking (release) — guarantees serializability
  • Strict: hold X locks till commit (no cascading aborts, no dirty)
  • Rigorous: hold ALL locks till commit (strict + recoverable)
⚠️ 2PL can deadlock — paired with timeouts/deadlock detectors + wait-die/wound-wait.
LockUse
S / XRead / write row
IS / IXTable-level intent (hierarchy, fast conflict check)
Gap / Next-key (InnoDB)Lock index gaps to block phantoms in RR
-- optimistic: check version on write
UPDATE items SET stock=stock-1, ver=ver+1
WHERE id=5 AND ver=7;  -- 0 rows = conflict, retry

Pessimistic (SELECT FOR UPDATE) blocks upfront — better under high contention; OCC better when conflicts rare.

MVCC keeps multiple row versions (xmin/xmax). Readers see snapshot as-of start; writers create new versions + garbage-collect old (VACUUM). Gives non-blocking reads in RC/RR; writes still conflict on same row.

💡 Postgres/InnoDB MVCC is why SELECTs don't block UPDATEs — unlike old lock-everything DBs.

Each txn gets TS; ops allowed only in TS order (abort + restart violators). Thomas rule: skip obsolete writes (late write on already-newer value) instead of aborting — safe for WW only.

  • Detection: cycle in wait-for graph → abort victim (youngest/cheapest)
  • Timeouts: lock_timeout / innodb_lock_wait_timeout — simple, may false-abort
  • Prevention: wait-die (old waits, young dies) / wound-wait (old preempts young)
SELECT * FROM jobs WHERE status='new' LIMIT 1
FOR UPDATE SKIP LOCKED;  -- queue pattern: grab unlocked job, skip busy ones
  • Short txns, update last, batch increments
  • Partition counters (sharded sums)
  • Advisory locks / queues for serialization
  • OCC retry with exponential backoff

Postgres SERIALIZABLE runs MVCC + tracks RW dependencies; aborts on dangerous structures (cycle risk). You get serializability without full locking — but must retry serialization failures (40001).

Recovery & Logging
Q85 – Q91

Log change before data pages. ARIES: Analysis (who was active), Redo (replay history incl. losers), Undo (rollback losers). Gives atomicity + durability with physiological (page-oriented) logging.

  • STEAL: uncommitted pages may hit disk → need UNDO
  • FORCE: commit forces all pages → slow, needs no REDO

Modern DBs use STEAL + NO-FORCE (fast) → need both UNDO + REDO via WAL.

Checkpoint flushes dirty pages + writes LSN. Bounds REDO scan on restart. Fuzzy checkpoints don't stall traffic (background flush); sharp pauses (rare now).

  • Crash: replay WAL automatically
  • Media (disk dead): restore base backup + replay WAL to point-in-time (PITR)
  • Logical (oops DELETE): flashback / delayed replica / logical dump restore
pg_basebackup + WAL archive → recovery_target_time='...'

Shadow paging: copy-on-write page table, flip root on commit — no UNDO/REDO, but fragmentation + GC + hard for concurrent txns (SQLite classic). Logging (WAL) scales better for concurrent OLTP.

Durability = WAL fsync'd before COMMIT ack. fsync is slow → group commit batches flushes; synchronous_commit=off trades last-ms risk for speed. Battery-backed cache / SSD PLP hides latency.

SyncAsync
Data lossZero (on commit)Possible lag window
LatencyHigherLow
FailoverSafe promoteRisk split-brain / loss
💡 Quorum (e.g., 2 of 3) balances both — etcd/Raft style.

Storage & Indexing
Q92 – Q100
  • Heap: unordered pages + free-space map (Postgres default)
  • Clustered (InnoDB): table IS the PK B+tree — PK lookups fast, secondary needs PK hop
  • Pages: 8KB (PG) / 16KB (InnoDB) with slot directory + tuples

Balanced, shallow, sorted + linked leaves → O(log n) point + fast range scans. 16KB page, ~200 keys/branch → 3 levels ≈ 8M rows. All data in leaves (B+), internal nodes only guides.

IndexBest for
B-Tree=, <>, ORDER BY, LIKE 'pre%'
Hash= only (rarely needed now)
GINArrays, JSONB, FTS (inverted)
GiSTGeo, ranges, nearest-neighbor
BRINHuge append-only (time-series, min-max per block)

Order equality first, then range, then sort. Index (a,b,c) serves a=? AND b=?, a=?, but NOT b=? alone. High-selectivity first is a myth — think query patterns, not cardinality alone.

CREATE INDEX ON Orders(status, created_at); -- WHERE status=? ORDER BY created_at

If index has all needed columns, engine never touches heap (fast). Use INCLUDE for payload without bloating key order:

CREATE INDEX ON Users(email) INCLUDE(name);
CREATE INDEX ON Orders(created_at) WHERE status='open'; -- small, hot subset
CREATE INDEX ON Users(LOWER(email));  -- match expression in query!
CREATE UNIQUE INDEX ON Users(email) WHERE deleted_at IS NULL; -- soft-delete uniqueness
  1. Function on column (YEAR(d) vs range)
  2. Leading wildcard LIKE '%x'
  3. Implicit cast (text = int)
  4. Low selectivity + small table (seq scan cheaper)
  5. Stale stats (run ANALYZE)
  6. OR across columns (use UNION)
  7. Wrong column order in composite
🔍 Check EXPLAIN (ANALYZE, BUFFERS): Seq Scan + high rows = missing/wrong index.
  • Seq scan: full table — OK small, bad large
  • Bitmap heap: many matches combined efficiently
  • Nested loop: tiny outer + indexed inner
  • Hash/merge join: large equijoins (hash builds table, merge needs sort)

MVCC leaves dead tuples → VACUUM reclaims + freezes; ANALYZE updates stats; autovacuum does both. Bloat = dead space; fillfactor <100 reserves room for HOT updates on same page.

CAP: during Partition, pick Consistency or Availability. PACELC: Else (no partition), pick Latency or Consistency. CP: etcd, HBase; AP: Cassandra, Dynamo (tunable quorum); Postgres = CA single-node (partition = downtime).

  • Replication: copies for availability/reads (primary-replica)
  • Sharding: split rows across nodes by key (writes scale; cross-shard joins hard)
  • Partitioning: split single node table (range/list by date) for manageability
⚠️ Pick shard key with high cardinality + even spread (user_id, not country).

Keys + nodes on a hash ring; each key → next node. Adding node moves only ~1/n keys. Virtual nodes smooth skew. Hotspot = celebrity key overloads one node → split/cache it.

  • Types: string (sessions), hash (objects), sorted set (leaderboards), stream (queues)
  • Cache-aside: app checks cache, falls back to DB
  • Write-through/behind: sync vs async DB write
⚠️ Stampede: many misses hit DB at once — use request coalescing + jittered TTL.

Document fits whole-object reads, evolving schemas, hierarchical data. Postgres JSONB + GIN gives docs + joins + ACID in one engine — often beats adding Mongo just for "flexibility". Use native Mongo for Atlas scale-out + document-native tooling.

Design, Tuning & Misc
Q107 – Q110
// BAD: 1 + N queries (ORM loop)
users.each { u -> u.orders }  // 101 queries!
// GOOD: eager load / join / IN batch
SELECT * FROM users JOIN orders ON orders.user_id=users.id;
// or DataLoader / includes(:orders)

Each conn costs RAM + backend process + lock contention. Little's law: pool ≈ cores × 2 + spindles. PgBouncer in transaction mode multiplexes thousands of app conns onto few DB conns. 2000 direct conns = context-switch meltdown.

  1. EXPLAIN (ANALYZE, BUFFERS) — scan type + actual vs estimated rows
  2. Missing index? Wrong order? Function on column?
  3. Lock waits? (pg_stat_activity)
  4. Stats fresh? (ANALYZE)
  5. Rewrite: EXISTS vs IN, UNION ALL, keyset pagination, covering index
  6. Cache/pool/materialize if still hot
  1. Logical order: FROM→WHERE→GROUP→HAVING→SELECT→ORDER→LIMIT
  2. NULL is UNKNOWN: use IS NULL / NOT EXISTS, not = / IN with NULLs
  3. LEFT JOIN + WHERE on right = INNER; put filter in ON
  4. 2NF kills partial deps; 3NF kills transitive; BCNF: every determinant is key
  5. RC blocks dirty; RR blocks non-repeatable; Serializable blocks phantoms
  6. Strict 2PL holds X till commit; MVCC lets readers never block
  7. WAL before data; STEAL+NO-FORCE needs UNDO+REDO
  8. B+Tree default; composite (equality, range, sort); covering = index-only
  9. OFFSET is slow; keyset paginate; UNION ALL > UNION
  10. Pool small (cores×2), N+1 via eager load, EXPLAIN everything
🔍 Say the trade-off out loud — interviewers score reasoning, not recall.
