Java Platform
Q1 – Q6

Java became dominant because of a unique combination of features that addressed real pain points of the 1990s software world:

  • Platform Independence – Write Once, Run Anywhere (WORA). Compile to bytecode, run on any JVM.
  • Object-Oriented – Everything is an object. Promotes code reuse, modularity, and clean design.
  • Automatic Memory Management – Garbage Collector handles allocation/deallocation; no manual free().
  • Strongly Typed & Safe – Type safety, array bounds checking, no raw pointers.
  • Rich Standard Library – Collections, I/O, networking, concurrency — all built in.
  • Multi-threading Support – First-class threading APIs baked in.
  • Massive Ecosystem – Spring, Hibernate, Maven, Android — decades of tooling.

Platform independence means the same compiled Java code runs on any OS without modification. Achieved via the JVM abstraction layer.

// Step 1: Write Java source → Step 2: javac compiles to .class (bytecode)
// Step 3: Any JVM on any OS interprets that bytecode
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}
💡 The JVM itself is NOT platform-independent — but your Java code is.

Bytecode is the intermediate binary representation produced by javac — neither raw source nor native machine code. It's OS-agnostic and runs on any JVM.

// javap -c Hello.class  (simplified view)
0: getstatic     #2   // Field java/lang/System.out
3: ldc           #3   // String "Hello"
5: invokevirtual #4   // Method println
8: return

The JVM can interpret bytecode or JIT-compile it to native code for performance.

The ClassLoader loads .class files into JVM memory at runtime. Three built-in loaders (delegation hierarchy):

  • Bootstrap – Loads core Java classes (java.lang.*). Written in native code.
  • Extension/Platform – Loads from jre/lib/ext.
  • Application – Loads your app classes from classpath.
ClassLoader cl = MyClass.class.getClassLoader();
System.out.println(cl);                 // AppClassLoader
System.out.println(cl.getParent());     // PlatformClassLoader
System.out.println(cl.getParent().getParent()); // null (Bootstrap)
💡 Custom ClassLoaders power hot-reload in Spring Boot DevTools, OSGi, and Tomcat.

Autoboxing is the automatic conversion between a primitive and its Wrapper class, done by the Java compiler.

Integer x = 5;     // autoboxing: compiled as Integer.valueOf(5)
int     y = x;     // unboxing:   compiled as x.intValue()

List<Integer> list = new ArrayList<>();
list.add(10);              // autoboxed
int val = list.get(0);    // unboxed
  • Less boilerplate – No manual valueOf/intValue calls everywhere.
  • Cleaner generic code – list.add(5) instead of list.add(Integer.valueOf(5)).
  • Interoperability – Primitives and Wrappers mix naturally in expressions.
⚠️ Watch out: unboxing a null Wrapper throws NullPointerException! 
Integer i = null;
int val = i;  // NullPointerException — calls null.intValue()

Casting is converting a value from one type to another. Two kinds: implicit (widening) and explicit (narrowing).

int i = 42;
double d = i;         // implicit — int → double, no data loss
int back = (int) d;  // explicit — double → int, may truncate

Widening conversion — happens automatically when assigning a smaller type to a larger type. No data is lost.

byte  b = 10;
short s = b;   // byte → short
int   i = s;   // short → int
long  l = i;   // int → long
float f = l;   // long → float
double d = f;  // float → double
// Order: byte → short → int → long → float → double

Narrowing conversion — you must manually specify the target type. Data loss is possible.

double d = 9.99;
int i = (int) d;        // truncates → i = 9

// Object casting
Object obj = "Hello";
String s = (String) obj;     // OK
// Integer n = (Integer) obj; // ClassCastException at runtime!

// Safe with instanceof (Java 16+ pattern matching)
if (obj instanceof String str) {
    System.out.println(str.length());
}

Strings
Q16 – Q22

Yes — java.lang.String objects are always immutable. Any "modification" creates a new String object.

String s = "Hello";
s.toUpperCase();         // returns new String — s unchanged!
System.out.println(s);  // still "Hello"

s = s.toUpperCase();     // now s points to new "HELLO" object
💡 Immutability makes Strings thread-safe, safe as HashMap keys, and enables the String Pool optimization.

String literals go into the String Pool (part of the Heap since Java 7+). The JVM reuses pooled Strings to save memory.

String a = "Java";            // stored in pool
String b = "Java";            // reuses same pool object
System.out.println(a == b);   // true  — same reference

String c = new String("Java"); // always new heap object
System.out.println(a == c);   // false — different object
System.out.println(a == c.intern()); // true — intern() forces pool

Because String is immutable, each + creates a new String object, copying all previous content. This is O(n²) time and memory.

// BAD — O(n²)
String result = "";
for (int i = 0; i < 10000; i++) {
    result += i;  // new String object every iteration!
}
// At iteration n: copies n characters → total = 1+2+...+10000 ≈ 50M copies

Use StringBuilder — uses a mutable char array internally, appending is O(1) amortized.

// GOOD — O(n)
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 10000; i++) {
    sb.append(i);
}
String result = sb.toString();

// Or with streams:
String s = IntStream.range(0, 10000)
    .mapToObj(Integer::toString)
    .collect(Collectors.joining());

Object Oriented Programming Basics
Q23 – Q54

A class is a blueprint/template defining the structure (fields) and behavior (methods) of objects.

public class Car {
    private String brand;  // state
    private int speed;
    public Car(String brand) { this.brand = brand; }
    public void accelerate(int amount) { speed += amount; } // behavior
}

An object is a concrete instance of a class — exists on the heap with its own copy of the state.

Car myCar  = new Car("Toyota");
Car yourCar = new Car("Honda"); // separate object, separate state
myCar.accelerate(60);
System.out.println(yourCar.getSpeed()); // 0 — independent

The state is the set of values held in an object's instance variables at a given moment — "what the object currently knows."

Car car = new Car("BMW"); // state: brand="BMW", speed=0
car.accelerate(100);      // state: brand="BMW", speed=100

The behavior is what an object can do — defined by its methods. Behavior reads or modifies state, or interacts with other objects.

// Behaviors of a Car:
car.accelerate(50);   // changes state
car.brake();          // changes state
car.getSpeed();       // reads state
car.honk();           // side effect / environment interaction

java.lang.Object is the root superclass of every Java class.

// Key methods inherited from Object:
obj.toString()    // "ClassName@hashcode" by default
obj.equals(other) // reference equality by default
obj.hashCode()    // identity hash code
obj.getClass()    // returns Class<?>
obj.clone()       // shallow copy (needs Cloneable)
obj.wait()        // thread coordination
obj.notify()      // thread coordination

toString() returns a human-readable string of an object. Called automatically on print/concat. Override for useful output.

// Default: Car@1b6d3586 — not useful
@Override
public String toString() {
    return "Car{brand='" + brand + "', speed=" + speed + "}";
}
System.out.println(new Car("BMW")); // Car{brand='BMW', speed=0}

equals() is for logical/content equality. Default from Object checks reference equality (same as ==). Override it to compare fields.

String a = new String("hello");
String b = new String("hello");
a == b        // false — different refs
a.equals(b)   // true  — same content

The equals contract (from Object Javadoc):

  • Reflexive: x.equals(x) = true
  • Symmetric: x.equals(y) ↔ y.equals(x)
  • Transitive: x=y and y=z → x=z
  • Consistent: same result on repeated calls
  • Null-safe: x.equals(null) must return false
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Point p)) return false;
    return x == p.x && y == p.y;
}
⚠️ Always override hashCode() when you override equals() — or HashMap/HashSet will break.

hashCode() returns an integer used by hash-based collections (HashMap, HashSet) to determine storage buckets.

Contract: if a.equals(b) → a.hashCode() == b.hashCode(). The reverse is not required (hash collisions are OK).

@Override
public int hashCode() {
    return Objects.hash(x, y); // easy and correct
}

// Without proper hashCode, HashMap lookup fails:
Map<Point, String> map = new HashMap<>();
map.put(new Point(1,2), "A");
map.get(new Point(1,2)); // null — if hashCode not overridden!

Inheritance lets a subclass acquire fields and methods of a superclass via extends.

class Animal {
    String name;
    void eat() { System.out.println(name + " eats"); }
}
class Dog extends Animal {
    void bark() { System.out.println(name + " barks"); }
}
Dog d = new Dog();
d.name = "Rex";
d.eat();   // inherited — "Rex eats"
d.bark();  // own method — "Rex barks"

Multiple methods with same name but different parameter lists in the same class. Resolved at compile-time (static polymorphism).

class Calculator {
    int    add(int a, int b)          { return a + b; }
    double add(double a, double b)   { return a + b; }
    int    add(int a, int b, int c) { return a + b + c; }
    // NOTE: return type alone does NOT make overloading
}

A subclass provides a new implementation for a superclass method. Same name, same signature. Resolved at runtime (dynamic polymorphism).

class Animal { void sound() { System.out.println("..."); } }
class Cat extends Animal {
    @Override
    void sound() { System.out.println("Meow"); }
}
Animal a = new Cat();
a.sound();  // "Meow" — runtime dispatch picks Cat's version

No — Java forbids multiple class inheritance (Diamond Problem). But a class can implement multiple interfaces.

// class C extends A, B { }  ← COMPILE ERROR

interface Flyable  { void fly(); }
interface Swimmable { void swim(); }

class Duck implements Flyable, Swimmable {
    public void fly()  { System.out.println("Duck flies"); }

An interface is a contract defining what a class must do without specifying how. From Java 8+, interfaces can have default and static methods with bodies.

interface Shape {
    double area();  // abstract — must implement
    default void describe() {  // Java 8+ — optional override
        System.out.println("Area: " + area());
    }
    static Shape circle(double r) {  // Java 8+ static factory
        return () -> Math.PI * r * r;
    }
}
public interface Printable {
    int MAX_SIZE = 100;         // implicitly public static final
    void print();               // implicitly public abstract
    default void printTwice() { print(); print(); }  // Java 8+
    static void help() { System.out.println("Implement print()"); }
}
class Document implements Printable {
    private String content;
    @Override
    public void print() { System.out.println(content); }
    // printTwice() is inherited from interface default
}
Printable p = new Document();
p.print(); p.printTwice();
  • All fields are implicitly public static final.
  • All methods are implicitly public abstract (unless default/static).
  • You cannot instantiate an interface directly.
  • Diamond problem with default methods: if two interfaces share a default method, the implementing class MUST override it.
interface A { default void greet() { System.out.println("Hi A"); } }
interface B { default void greet() { System.out.println("Hi B"); } }

class C implements A, B {
    @Override
    public void greet() { A.super.greet(); } // must resolve explicitly
}

Yes — an interface can extend one or more interfaces.

interface Readable  { void read(); }
interface Writable  { void write(); }
interface ReadWrite extends Readable, Writable {
    void flush();
}
// Implementing class must fulfill all 3 methods

Yes — a class can implement multiple interfaces. (Classes implement; interfaces extend.)

class SmartPhone implements Callable, Browsable, Photographable {
    public void call()      { /* ... */ }
    public void browse()    { /* ... */ }
    public void takePhoto() { /* ... */ }
}

A class declared with abstract that cannot be instantiated. Can have both abstract methods (no body) and concrete methods.

abstract class Vehicle {
    protected String fuel;
    void refuel() { System.out.println("Refueling..."); } // concrete
    abstract void move();                                  // abstract
}
class EV extends Vehicle {
    @Override void move() { System.out.println("Silent zoom"); }
}
// new Vehicle() — COMPILE ERROR
  • You want to share common implementation among related classes.
  • You need non-public members (protected fields, package-private methods).
  • You need shared state (instance fields) — interfaces can't hold instance state.
  • You want a template method pattern — skeleton algorithm, subclasses fill in steps.
abstract class DataProcessor {
    final void process() { readData(); processData(); writeData(); }
    abstract void processData(); // subclasses define this
    void readData()  { /* default */ }
    void writeData() { /* default */ }
}
abstract class Shape {
    public abstract double area();      // no body — ends with ;
    public abstract double perimeter();

    public void describe() {  // concrete — has body
        System.out.printf("Area=%.2f%n", area());
    }
}
// Rules:
// - Abstract method ONLY in abstract class (or interface)
// - Subclass MUST implement ALL abstract methods, or itself be abstract

A no-arg constructor automatically provided by the compiler if you don't define any constructor yourself.

class Box {
    int width;
    // Compiler generates: Box() { super(); }
}
Box b = new Box(); // OK

class Box2 {
    Box2(int w) { } // custom constructor defined
    // Box2() no longer auto-generated!
    // new Box2() → COMPILE ERROR

Use super() as the very first statement in the constructor.

class Animal {
    String name;
    Animal(String name) { this.name = name; }
}
class Dog extends Animal {
    String breed;
    Dog(String name, String breed) {
        super(name);   // ← MUST be first statement
        this.breed = breed;
    }
}

this() is used for constructor chaining — calling another constructor of the same class to avoid duplication.

class Person {
    String name; int age; String city;

    Person(String name)                      { this(name, 0); }
    Person(String name, int age)             { this(name, age, "Unknown"); }
    Person(String name, int age, String city) {
        this.name = name; this.age = age; this.city = city;
    }
}
💡 this() must be the FIRST statement. You cannot use both this() and super() in the same constructor.

Advanced Object Oriented Concepts
Q53 – Q63

Polymorphism means "many forms" — an object behaving differently depending on the context. Two types in Java:

  • Compile-time (static) — method overloading. Resolved by the compiler.
  • Runtime (dynamic) — method overriding via inheritance. Resolved by JVM at runtime.
// Compile-time polymorphism
class Printer {
    void print(String s) { System.out.println(s); }
    void print(int n)    { System.out.println(n); }
}

// Runtime polymorphism
class Animal  { void speak() { System.out.println("..."); } }
class Dog extends Animal { void speak() { System.out.println("Woof"); } }
class Cat extends Animal { void speak() { System.out.println("Meow"); } }

Animal[] animals = { new Dog(), new Cat() };
for (Animal a : animals) a.speak(); // Woof, Meow

instanceof checks whether an object is an instance of a given class or implements an interface at runtime. Returns boolean.

Animal a = new Dog();
System.out.println(a instanceof Animal);  // true
System.out.println(a instanceof Dog);     // true
System.out.println(a instanceof Cat);     // false

// Traditional pattern
if (a instanceof Dog) {
    Dog d = (Dog) a;
    d.bark();
}

// Java 16+ pattern matching — cleaner!
if (a instanceof Dog d) {
    d.bark();  // d is already cast and bound
}
💡 null instanceof AnyType always returns false — never throws NPE.

Coupling measures how much one class depends on another. The goal is loose coupling — changes in one class should minimally impact others.

Tight CouplingLoose Coupling
DependencyConcrete classInterface / abstraction
TestabilityHard to mockEasy to mock
ChangeabilityRipple effectsIsolated changes
// TIGHT — Engine knows about exactly one Fuel type
class Engine {
    Petrol fuel = new Petrol(); // hard dependency
}

// LOOSE — Engine depends on an abstraction
interface Fuel { void combust(); }
class Engine {
    Fuel fuel; // inject any Fuel implementation
    Engine(Fuel fuel) { this.fuel = fuel; }
}

Cohesion measures how focused a class is on a single, well-defined responsibility. The goal is high cohesion.

// LOW cohesion — does everything badly
class UserManager {
    void registerUser() { }
    void sendEmail() { }
    void generateReport() { }
    void saveToDatabase() { }
}

// HIGH cohesion — each class has one clear job
class UserService   { void register() { } }
class EmailService  { void send() { } }
class ReportService { void generate() { } }
💡 High cohesion + Loose coupling = the SOLID principles in action.

Encapsulation is bundling data (fields) and methods that operate on that data into a single unit, and restricting direct access to internal state via access modifiers.

public class BankAccount {
    private double balance;  // hidden — can't be touched directly

    public void deposit(double amount) {
        if (amount > 0) balance += amount;  // controlled access
    }
    public double getBalance() { return balance; }
}

BankAccount acc = new BankAccount();
// acc.balance = -1000; ← COMPILE ERROR — encapsulated!
acc.deposit(500);

Benefits: data integrity, controlled mutations, abstraction, easier testing.

An inner class is a class defined inside another class. It has access to all members (including private) of the outer class.

class Outer {
    private int x = 10;

    class Inner {          // non-static inner class
        void show() {
            System.out.println("x = " + x);  // accesses outer's x
        }
    }
}

Outer outer = new Outer();
Outer.Inner inner = outer.new Inner(); // needs outer instance
inner.show();  // x = 10

A static nested class is declared with static. It does NOT hold a reference to the outer instance — can only access outer's static members.

class Outer {
    private static int count = 5;
    private int val = 10;  // non-static — inaccessible from static nested

    static class Nested {
        void show() {
            System.out.println(count);  // OK — static member
            // System.out.println(val); ← COMPILE ERROR
        }
    }
}

Outer.Nested n = new Outer.Nested(); // no outer instance needed!
n.show();
💡 Builder pattern commonly uses static nested classes (e.g., AlertDialog.Builder).

Yes — this is called a local class. It's defined inside a method and can only be used within that method. Can access effectively-final local variables.

void doSomething() {

An anonymous class is a class defined and instantiated in one expression — no name. Used to provide one-off implementations of an interface or abstract class.

// Without lambda — anonymous class

g.greet();

Modifiers
Q62 – Q76

When a class has no access modifier, it has package-private (default) access — visible only within the same package.

// File: com/example/Helper.java
class Helper {          // no modifier — package-private
    void assist() { }
}

// com.example.Service — same package — OK
Helper h = new Helper();

// com.other.Client — different package — COMPILE ERROR
// Helper h = new Helper(); ← inaccessible

private is the most restrictive modifier. Members are accessible only within the same class.

public class Account {
    private double balance;     // only Account can touch this
    private void validate() { } // only Account can call this

    public void deposit(double amt) {
        validate();       // OK — same class
        balance += amt;   // OK — same class
    }
}
// new Account().balance = 0; ← COMPILE ERROR outside Account

When no modifier is written, the member is accessible to all classes in the same package only.

package com.example;

class Util {
    int helperValue = 42;   // package-private field
    void doWork() { }       // package-private method
}

// com.example.Service — same package ✅
// com.other.App       — different package ❌

protected members are accessible within the same package AND by subclasses (even in different packages).

package animals;
public class Animal {
    protected String name;
    protected void breathe() { System.out.println("breathing"); }
}

package pets; // different package!
import animals.Animal;
class Dog extends Animal {
    void show() {
        name = "Rex";  // ✅ subclass can access protected
        breathe();     // ✅ same
    }
}

public is the least restrictive modifier. Accessible from anywhere — any class, any package.

public class MathUtils {
    public static double PI = 3.14159;
    public static double sqrt(double n) { return Math.sqrt(n); }
}

// Accessible from ANYWHERE:
System.out.println(MathUtils.PI);
System.out.println(MathUtils.sqrt(16)); // 4.0

A final method cannot be overridden by subclasses. Guarantees the method's behavior remains unchanged in the inheritance hierarchy.

class Template {

        execute();
        teardown();

    void execute() { }      // overrideable — subclass fills in
}

class ConcreteTask extends Template {
    @Override void execute() { System.out.println("Doing task"); }

}

volatile tells the JVM that this variable may be accessed by multiple threads. It guarantees:

  • Visibility – Every read sees the latest write from any thread (no CPU cache staleness).
  • No reordering – Writes/reads to volatile aren't reordered past each other.

It does NOT guarantee atomicity for compound operations like i++.

class StopFlag {
    volatile boolean running = true; // all threads see latest value

    void stop() { running = false; }

    void work() {
        while (running) { /* do work */ }
        // without volatile, loop might never see running=false!
    }
}

// For compound ops, use AtomicInteger instead:
AtomicInteger counter = new AtomicInteger();
counter.incrementAndGet(); // thread-safe i++

A static variable belongs to the class itself, not to individual instances. There is only one copy, shared by all objects of the class.

class Counter {
    static int count = 0;  // ONE copy shared by all instances
    int id;                // each instance gets its own id

    Counter() {
        count++;
        id = count;
    }
}

Counter c = new Counter();

System.out.println(a.id);           // 1

Exception Handling
Q91 – Q108

Without exception handling, any unexpected condition crashes the program. Exception handling provides:

  • Separation of concerns — error handling is separate from business logic.
  • Graceful degradation — app recovers or fails meaningfully instead of crashing.
  • Resource safety — finally/try-with-resources ensures cleanup even on failure.
  • Informative errors — stack traces tell you exactly where and why something broke.
try {
    int result = 10 / Integer.parseInt(input);
} catch (NumberFormatException e) {
    System.out.println("Invalid number: " + input);
} catch (ArithmeticException e) {
    System.out.println("Cannot divide by zero");
}

The Chain of Responsibility pattern. When an exception is thrown, it travels up the call stack looking for a matching handler. Each method either handles it or passes it to its caller.

// Call stack: main() → processOrder() → validatePayment() → throws
void main() {
    try { processOrder(); }
    catch (PaymentException e) { System.out.println("Caught: " + e.getMessage()); }
}
void processOrder() throws PaymentException { validatePayment(); }
void validatePayment() throws PaymentException { throw new PaymentException("Declined"); }
💡 If no handler is found all the way up to main(), the JVM prints the stack trace and terminates the thread.

The finally block always executes — whether an exception was thrown, caught, or didn't happen. Used for guaranteed resource cleanup.

Connection conn = null;
try {
    conn = getConnection();
    processData(conn); // might throw
} catch (SQLException e) {
    log.error("DB Error", e);
} finally {
    if (conn != null) conn.close(); // ALWAYS runs — no leak!
}
  • System.exit() is called — JVM terminates immediately.
  • JVM crash — OutOfMemoryError or native crash kills the process.
  • Thread killed externally.
  • Infinite loop in try/catch that never reaches finally.
try {
    System.out.println("try");
    System.exit(0); // JVM shuts down HERE
} finally {
    System.out.println("finally"); // NEVER runs
}

    System.out.println("try");
    int[] arr = new int[5];
    arr[10] = 42; // ArrayIndexOutOfBoundsException
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("catch");
} finally {
    System.out.println("finally");

Try-with-resources (Java 7+) automatically closes resources implementing AutoCloseable when the block exits — no finally needed.

// Old way — verbose, error-prone

try { br = new BufferedReader(new FileReader("f.txt"));
      System.out.println(br.readLine());
} finally { if (br != null) br.close(); }

// New way — clean and safe
try (BufferedReader br = new BufferedReader(new FileReader("f.txt"))) {
    System.out.println(br.readLine());
} // br.close() called automatically!

try (Connection c = getConn(); PreparedStatement ps = c.prepareStatement(sql)) {
    ps.executeQuery();
} // ps closed first, then c

The compiler transforms it into try-finally, handling suppressed exceptions — if both body and close() throw, the body exception is primary and the close exception is attached as suppressed.

// Implement AutoCloseable to participate in try-with-resources
class MyResource implements AutoCloseable {
    @Override
    public void close() { System.out.println("Resource closed"); }
    public void doWork() { System.out.println("Working"); }
}

try (MyResource r = new MyResource()) {
    r.doWork();
}
// Output:
// Working
// Resource closed  ← automatic!

try { } catch(Exception primary) {
